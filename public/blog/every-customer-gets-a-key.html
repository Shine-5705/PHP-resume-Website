Every Customer Gets Their Own Key

Sep 2026 7 min read
Turning Re-Forge from one team's tool into a product other teams could join
Engineering Re-Forge Security

Re-Forge started the way most internal tools do: it worked, it was ours, and exactly one secret proved that. Every device our hooks ran on carried the same token. It authenticated every request, it could read every session anyone on the team had ever captured, and it could revoke anyone's access - because it was everyone's access, all at once. That trade is fine when "everyone" is two founders and a laptop each. It stops being fine the moment a second company wants to run Re-Forge on their own team.

This is the record of what that transition actually cost - not the roadmap version, the one that includes the route an audit caught, the design decision I had to reverse in front of my own written rationale, and the one new piece of infrastructure it genuinely took to fix.

What one shared secret actually grants

I want to be precise about this, because "shared token" sounds abstract until you write down what it lets someone do. Our token authenticated every route: read every collected session, change server settings, revoke any device. Anyone who downloaded a build and inspected it had it. That's an acceptable trade for a two-person pilot. It is not something I would ever hand to a customer.

We had already been burned by the shape of this problem once, in miniature: an early version of our config endpoint returned more than it should have to a caller that hadn't proven who it was. The blast radius was small that time, because there was only one company's data behind it. The lesson generalized anyway: a single shared secret doesn't just risk a leak - it makes every future leak a leak of everything. Whatever replaced it had to shrink that number from "everyone" to "one person," by construction, not by policy.

The rule I wrote down before touching any code. A token identifies a person, not a download. Whatever boundary decides "which company's data is this" stays separate from whatever boundary decides "is this credential still good" - collapsing the two together is exactly how a shared secret happens in the first place.

The four things, not three

Say it out loud - a company, its people, its repositories - and the model sounds obvious. Mostly it is. What isn't obvious on the first pass is that people and repositories don't connect to each other directly. Two employees can push to the same repository from two different laptops, and neither of those laptops should ever see the other's captured sessions just because the code is shared. The thing that actually connects a person to a repository is the device sitting between them.

The route that got left behind

Before any of the multi-tenant work, I ran a plain audit of every network call our desktop app and our hooks make, against every route our backend actually serves. One didn't match. The device-join flow - what runs the first time a fresh install talks to our server - called an endpoint that had quietly stopped existing during an earlier rewrite. Nobody had noticed, for one reason: every device that had ever joined had joined before that rewrite. The bug only affects a device that has never joined before, and we hadn't shipped one of those in weeks.

That is the failure mode worth remembering: the code path with zero live users is the one with zero live signal that it's broken. It doesn't page anyone, it doesn't show up on a dashboard - it sits there until the day someone new tries to onboard, and that becomes their first impression of the product.

What would actually have caught this. Not more logging, not a smarter alert - a test that runs on every push and exercises exactly what a brand-new install does. We didn't have one. We do now.

The decision I had to reverse in public

Early on, I wrote down - deliberately, as a design principle - that Re-Forge should use one encryption key for everyone's sealed data, forever. The reasoning wasn't lazy: our own pipeline already decrypts everything under one role to run analysis, so separate keys per customer would have bought zero additional isolation for real engineering cost. For one customer, that reasoning is correct.

It stops being correct the moment a second company's data sits behind the same key. At that point, "one key for everyone" no longer describes an efficient system - it describes one company's departing employee and another company's confidential codebase sharing a lock. The fix was not clever: one key per customer, generated at provisioning, with our pipeline's decrypt role granted per key rather than once, globally. The part worth noting is that I had to go back to a document where I'd written "this is correct, don't revisit without re-reading why" and revisit it anyway - not because the reasoning was wrong, but because the situation it was reasoning about had changed underneath it.

A token doesn't say whose company it is

This is the part that forced genuinely new infrastructure, not just a policy change. With one org, checking a token means checking it against one list. With many, a request arrives carrying nothing but the token itself - nothing says which company's list to even look in. Scanning every customer's records on every request is both slow and the wrong tool for what is really just a lookup problem.

That lookup is the one new database this redesign actually needed - not a rewrite of where session data lives, just a fast index in front of it. How a session gets captured, sealed, and stored stayed exactly as it was. The table is small, cheap, and billed per request rather than for capacity sitting idle, which mattered to me more than it probably should have: not leaving a meter running on something nobody is using turns out to be most of what "production-grade" means at this scale.

The moment that justifies all of it

Everything above is infrastructure. Here is the product moment it exists for: someone leaves the team, or a laptop is compromised, and their access needs to be gone now, without touching anyone else's. Under the old shared-token design, that meant rotating one secret and breaking every other device that held it - or not rotating it, and carrying the risk. Under the new design, it is one action against one record, and the very next request from that person, from any device, on any route, is refused - while nobody else on the team notices anything happened.

How I actually proved this, not just designed it. I wrote a test that creates two fake companies, gives each one an admin, and asserts - by calling the real code path, not by reading the code and agreeing with it - that company A's admin gets nothing back when it tries to touch company B's people, even by guessing an exact internal ID. Then I proved the revocation case the same way: register a device, capture a real event, revoke the person, and check that the identical next request is refused. Design review tells you a system should be safe. A test that tries to break it and fails tells you it is.

What's proven, and what I'm not claiming yet

In the interest of the same honesty I try to hold my research writing to: the identity layer above is real, deployed, and I watched it work end to end - creation, sign-in, capture, revocation, all against the live system, not a staging copy. It does not yet include a full migration of every existing route onto the new per-person model (today it is a deliberate dual-auth transition, so nothing already working breaks mid-rollout), continuous integration running the isolation test on every push rather than the one time I ran it by hand, or per-customer rate limits to stop one company's misbehaving client from affecting another's. Those are named, tracked, and next - not quietly skipped.

The line I keep landing on, across this and the research side of what I do: the version of "it works" that counts is the one you watched fail in the way you predicted, not the one you're confident about because the design looked right on paper.
